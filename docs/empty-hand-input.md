# Empty-hand input behavior

The owner's saved configuration at `F:/McServers/Console/servers/latests/plugins/BeastDoubleWield/config.yml` was inspected on 2026-10-30. It had `swing.air: true`, `attack.allow-empty-hand: true`, `attack.correct-tool-only: false`, and `mine.allow-empty-hand: false`. The player preference file had no disabled players. No server configuration was changed during this investigation.

An input bug was identified: the listener accepted only main-hand callbacks even for air interactions. The installed vanilla 26.3 client's `net.minecraft.client.Minecraft.startUseItem()` loops over both hands, but calls `MultiPlayerGameMode.useItem()` only when that hand's stack is nonempty. Thus an empty main hand with a held offhand item can produce only an offhand air-use callback, which the old listener discarded. This was checked in the local official client JAR with `javap -c -p`; the empty-stack branch precedes `useItem` at bytecode offsets 376-394. Block/entity interactions occur before that empty-stack guard.

The input fix accepts `OFF_HAND` air callbacks when the main hand is empty, while retaining main-hand input support. It permits at most one eligible air input per player tick, including denied inputs, to prevent duplicate hand callbacks or a second callback bypassing a denial. Offhand block/entity callbacks remain ignored, with existing protection and interaction-priority checks intact. Input history is cleared when a player leaves, changes worlds or respawns.

Both empty hands still produce no vanilla right-click-air packet. `attack.allow-empty-hand` permits the offhand fist when a real interaction exists, such as right-clicking an entity. An ordinary non-use item in the main hand can also generate the air input needed for an empty offhand swing. It does not turn an undetectable client click into a server event. Empty-hand mining is controlled independently by `mine.allow-empty-hand`.

Rendering is a separate client restriction. In the same installed 26.3 client, `FirstPersonHandsAndItemsRenderer.submitArmWithItem()` records whether the hand is `MAIN_HAND` at offsets 20-33. If the item stack is empty, offsets 99-109 skip arm rendering for the offhand; `renderPlayerArm()` is reached only for the main hand. An empty-offhand attack or swing request therefore does not guarantee a visible offhand fist in first person. The plugin does not install a client mod or supply a custom arm model to change that rendering behavior.

Version 1.0 adds a separately opt-in main-hand placeholder on 1.14+ to solve the missing input signal. This is an actual disposable feather with CustomModelData `35021` and a private ownership tag; the example pack gives it an empty model. It has no lore and a blank visible name. It is created only in an eligible empty selected slot, and removed around inventory and lifecycle transitions. It still does not draw a bare offhand fist. See the [configuration instructions](../README.md#optional-invisible-main-hand-item), [pack examples](../examples/resourcepack/README.md), and the release-specific runtime evidence in [verification.md](verification.md).

The fix has input-boundary regression coverage; it was not tested through a live player session on the owner's running server. Existing runtime evidence for the earlier gameplay build is recorded separately in [verification.md](verification.md). No debugger connection was available for this investigation.

Primary API reference: [Spigot PlayerInteractEvent](https://hub.spigotmc.org/javadocs/bukkit/org/bukkit/event/player/PlayerInteractEvent.html) documents per-hand callbacks and vanilla-predicted cancellation. The plugin continues to honor item-use denial rather than clearing it to force a swing.
