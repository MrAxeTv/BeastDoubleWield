# First-person arm development record

This feature belongs to `1.1-SNAPSHOT` on `feature/first-person-arm`. The public `1.0` release and update feed remain unchanged. The older [verification record](verification.md) and export receipt describe that release; this document records the new optional arm work.

## Setup and behavior

Use **Paper 26.3 and a native Java 26.3 client**, with the [matching arm pack](../examples/firstperson-arm/README.md) manually enabled. Edit these keys in their existing `config.yml` sections, then run `/bdw reload`:

```yaml
OffhandArm:
  Enabled: true
Swing:
  Air: true
Attack:
  AllowEmptyHand: true
  CorrectToolOnly: false
```

An attack material whitelist must include `AIR`. Mining separately requires `Mine.AllowEmptyHand` and compatible mining rules. Existing permissions, personal/global switches, world rules, Survival/Adventure restrictions and spare-storage requirement still apply. Any free storage slot counts, including the selected hotbar slot. An existing eligible arm remains during unrelated inventory actions. Opening a container or clicking/dragging in an inventory pauses new arm insertion until the view closes; the cursor must also be empty. The new setting defaults to `false`.

The standalone `tools/build-firstperson-arm.ps1` builder now copies only the completed ZIP to `C:/Users/krist/AppData/Roaming/.minecraft/resourcepacks` by default and verifies the exported SHA-256. Identical bytes preserve the existing build and client ZIP timestamps. Use `-SkipClientExport` for isolated builds or `-ClientResourcePackDirectory <directory>` to choose another destination. The enabled-pack list and client resource reload remain manual. This local export does not offer the pack to server players or start/reload a server.

On 2026-10-31 the owner authorized this default export, and the corrected 58,401-byte pack was copied to the client folder with matching SHA-256 `b18c8699225424aca7e4c5cd2e4a4b1376056fcc1e5c2347850afc5b22da5f63`. A repeated build preserved the installed timestamp; the skip option created no destination; an isolated alternate destination matched the same hash. `options.txt` remained byte-identical during verification.

An otherwise empty offhand receives a privately marked FEATHER carrying the player's existing complete skin profile and the `minecraft:player_head` item model. CustomModelData `35022` selects classic arms; `35023` selects slim arms. Public Paper PROFILE component access preserves the profile on the feather after metadata edits. This avoids the placement and helmet-equipping behavior of a real head. Production code uses public APIs, with reflective discovery isolating newer APIs from the Java 8/legacy core path.

The shared pack reshapes native profile-head geometry and samples the bound skin's arm and sleeve regions. It does not need a generated skin PNG or a separate pack per player. The plugin does not fetch profiles while reconciling inventory. A missing complete skin leaves the offhand empty and is retried every 100 ticks. Skin changes appear when the carrier is recreated, such as after toggling or reconnecting.

The plugin never inserts a main-hand input feather. An empty main hand stays empty so Minecraft can render its ordinary arm; real main-hand items are preserved. A tool in the offhand already generates right-click input without a main-hand placeholder or pack. Real offhand items take priority over the optional arm. The arm counts as AIR for attack/mining filters and custom events; native actions temporarily receive actual AIR. Restoration preserves real items produced by other listeners. Cleanup relies on the private typed ownership tag, never just the item's name or model number, and still removes old tagged main-hand carriers after upgrades.

The pack renders the skin arm only in first-person hand contexts. GUI contexts show Minecraft's empty shield-slot silhouette with no tooltip; the same GUI context is used by the offhand HUD, so the icon also appears there. Third-person player geometry and swinging use Minecraft's ordinary animation. Holding an invisible item can still change the native resting arm pose; this is not a promise of an identical empty-hand posture in every camera mode.

## Single offhand arm switch (current 1.1 development)

Current setup examples use only the new section and its `Enabled` key; asset paths, private carrier identifiers and implementation class names retain their established names.

An explicitly saved `OffhandArm.Enabled` value takes priority over the old pair. This preserves the previous enabled/disabled behavior while removing the redundant setting.

Translation checks cover all 1,000 message values across the 50 files: keys, nonempty strings, placeholders, color codes, commands, branding and strict UTF-8. ## Successful mining break sound

The owner reported that offhand mining lacked the final block-break sound. An isolated regression and debugger trace reproduced a successful native break changing the block to AIR with zero sound calls to the acting player. Native-code inspection of the installed Paper 26.3, Spigot 1.20.2 and Spigot 1.9.4 paths confirmed that destruction broadcasts event 2001 to nearby players while excluding the actor. Ordinary left-click clients predict that effect locally; plugin-driven right-click mining has no equivalent prediction.

After custom-event/eligibility checks, the plugin now captures the original block's break sound before invoking the native break. On success it plays that sound only to the actor, at the block center, in the BLOCKS category, using the native volume `(volume + 1) / 2` and pitch `pitch * 0.8`. Cancellation or a false native result stays silent. Nearby players retain the native effect without a duplicate broadcast. Playback is skipped if a native listener disconnects the player or moves them to another world. Sound lookup/playback failures do not prevent destruction, erase success accounting or bypass the post-break delay. The existing `mine.sounds` toggle continues to control progress hit sounds only.

Servers without public SoundGroup use the older public, actor-only `STEP_SOUND` effect with a captured Material. This lets their client supply the sound/category and also restores local break particles, using the material's default state. Actual 1.9.4/1.12.2 Craft effect conversion and the 1.13.2 API/Craft conversion were inspected; the latter maps flattened materials to native default-state IDs (official CraftBukkit commit `06534f2adf0a7d9c115cccb8280171d7e566ecdf`). No new NMS reflection or numeric material-ID mapping was added. Modern playback supplies sound only. If another plugin replaces the block's type inside the native BlockBreakEvent, the captured pre-event sound can differ from that replacement; custom state-changing listeners are not certified by this fix.

## Mining input and speed corrections

The owner reported that offhand mining continued after releasing right-click and sometimes seemed faster than left-click mining. Two isolated regressions reproduced concrete timing differences: a single unrefreshed input could finish a block with eight ticks of progress, and a successful progressive break could immediately start the next block. Debugger traces captured both paths before changes.

The default `mine.inputProgressTicks` is now 4, separate from the existing 8-tick `mine.inputTimeoutTicks`. Silent ticks 1–4 may advance progress; ticks 5–8 retain the session without adding progress, swings or hit sounds; tick 9 expires it. Both controls accept whole values 2–40, and the progress window is capped by the timeout. Late input resumes retained progress without credit for missed ticks. The shorter window bounds speculative work after release to about 200 ms at 20 TPS, measured from the latest input rather than the physical release. A fast block can still finish inside that window. This does not claim exact button-up detection.

Installed native 26.3 inspection confirms ordinary held right-click repeats at four-client-tick intervals and emits no generic release notification. Active item-use release (for bows, for example) is separate. Native held-left-click mining has an explicit abort path and skips five continuation ticks after a progressive/Creative break. The plugin now blocks a new mining session through completion tick +5 and accepts a new input from +6. True instant Survival breaks, including a first-step native increment of at least 1 and skill-requested instant breaks, omit the pause. Denied breaks do not install it. Input cadence can delay the next start further; separate taps cannot be distinguished from held right-click repeats. A completion guard prevents native break listeners from starting another session before the result is known.

Native mining uses cached `MINING_EFFICIENCY`, `BLOCK_BREAK_SPEED` and `SUBMERGED_MINING_SPEED` attributes. Merely swapping the inventory does not refresh them. A separate regression observed a plain acting pickaxe retaining the main hand's Efficiency V contribution of 26. The new synchronous attribute scope switches hand-owned modifiers for the speed calculation, adjusts the exact vanilla Efficiency modifier, preserves unrelated attributes and restores changes after success or failure. Optional public APIs are discovered reflectively; no NMS dependency was added. The vanilla Efficiency correction uses the verified namespaced modifier/API path and does not promise to emulate custom data-pack enchantment effects.

The owner also asked about mace behavior. Static native-path inspection confirms that the swapped mace reaches native attack/smash processing. The existing optional offhand attack limiter can reject another default-speed mace attack for 34 ticks (about 1.7 seconds), while native Minecraft permits low-charge attacks. No mace-specific runtime failure has been reproduced, and the exact reported symptom is still needed before changing that policy. This mining change does not claim to fix or certify mace combat.

At the owner's request, the upstream mining implementation was read for comparison after the original independent implementation. It also infers release from recent input, using a 230 ms freshness check in a scheduled operation. See the updated [research boundary](feature-matrix.md#origin-and-research-boundary). No upstream source was copied or translated; these corrections follow the reproduced BeastDoubleWield failures and native behavior described above.

## Compatibility limits and live acceptance

The new renderer is deliberately limited to the verified **26.3** API/client combination. It does not extend the shader pack to 1.9 or imply that every server version is supported. Unsupported servers leave the offhand empty. Known local Geyser/Floodgate clients are excluded. Client eligibility requires a successful protocol query matching native 26.3 (`777`): local ViaVersion 5 supplies it when installed, otherwise Paper's public player protocol API does. Unknown/other protocols, unavailable queries and disabled/incompatible local ViaVersion do not receive a carrier. Paper sees the protocol presented by its connection; a translating proxy can mask the original client's protocol. Server owners must therefore still restrict the feature to matching clients.

The pack replaces entity core shaders and the player-head item definition. It **cannot be stacked with the current BeastRPGInventory 26.2 pack**. That pack needs a separately verified 26.3 port and an explicit merge. The owner's BeastMounts/ObjCubed 26.3 server pack also replaces both entity shaders and needs a verified merge before simultaneous use. Other shader replacements and rendering mods need their own checks. BeastRPGInventory sources and the user's installed packs were not changed.
